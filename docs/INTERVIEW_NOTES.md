# FinGuard Core 面试笔记

这些答案围绕项目中的真实决策、证据和限制，不背诵脱离上下文的定义。

## 1. 为什么选单体而不是微服务？

项目目标是练习业务一致性、异步可靠性和生产化验证。单体能让事务边界和故障定位保持清楚，又能通过 RabbitMQ、Redis、Prometheus 等真实依赖练习分布式边界。当前规模拆微服务只会增加部署和数据一致性成本，没有业务证据支持。

## 2. 为什么 MySQL 是真源，RabbitMQ 不是？

消息可能重复、延迟或丢失 ACK；业务任务必须能从数据库终态恢复。MySQL 保存任务、结果、幂等键和审计，RabbitMQ 只通知消费者处理哪个聚合。因此即使重复投递，也先读数据库并判断行锁和终态。

## 3. Transactional Outbox 解决什么问题？

它把“创建业务任务”和“记录待发事件”放在同一数据库事务，避免数据库提交成功但消息未发送的双写窗口。Relay 后续发布并记录 SENT；即使重复发布，消费者仍由数据库幂等兜底。

## 4. 为什么消费者要手动 ACK？

只有事务成功提交后 ACK，才能避免处理未完成却确认消息。若提交后 ACK 丢失，消息会重投，所以还必须有终态检查、唯一约束和行锁；手动 ACK 本身不等于 exactly-once。

## 5. 如何处理重复消息？

消息携带稳定 ID 和聚合 ID，但消费者不信任消息中的业务统计。处理时锁定任务行，终态直接返回；写入由唯一键保护，审计也按目标唯一。这样“至少一次”传递能得到业务上的幂等效果。

## 6. 为什么重试是 5 秒、30 秒两级而不是无限重试？

有限重试适合短暂依赖故障，同时限制阻塞和消息风暴。两次仍失败就进入独立 DLQ 并保留固定失败分类，交给人工诊断。无限重试会让毒消息长期占用消费者并掩盖故障。

## 7. 对账算法如何取舍？

先按外部流水号精确匹配，再按账户、方向、金额和三天时间窗口做容差候选。每批最多查 500 个账户的候选，再在内存按 `(transaction_time,id)` 稳定计算，避免逐笔 SQL。结果显式区分匹配、无匹配、重复候选和可疑不一致。

## 8. 风险规则为什么不用 Drools？

当前只有三条固定规则，类型安全配置、纯函数规则和明确原因码更易测试、部署和解释。没有动态规则运营或热更新需求时，引入规则平台会扩大复杂度。若未来规则数量、版本和审批需求增长，再评估 DSL/规则引擎。

## 9. 审核并发如何避免覆盖？

客户端提交当前 `version`，数据库执行 `id + status=PENDING + version` 条件更新。更新数为 0 后再区分任务不存在、已终态和版本冲突，分别返回 404 或稳定 409。审核人从 JWT subject 获取，不能由请求体伪造。

## 10. 为什么同时需要应用校验和数据库约束？

应用校验提供清晰错误，但并发请求可能都通过预查。唯一键、CHECK、外键和条件更新是最终一致性防线。两层组合既有用户友好响应，也能在竞态下保证数据不变量。

## 11. 401 与 403 的区别？

401 表示没有合法身份，例如缺少、篡改或过期 Token；403 表示身份已经验证，但角色无权执行操作。项目用真实过滤链测试匿名 401、REVIEWER 写操作 403 和 ADMIN 对审核决策 403。

## 12. JWT 为什么不是加密数据？

JWT Payload 可被客户端解码；HS256 签名保证未被篡改和签发方可信，不隐藏内容。因此 Token 只放 subject、issuer、时间和角色，不放密码、哈希或业务敏感数据。

## 13. 无状态 JWT 的代价是什么？

服务端无需 Session，但已签发 Token 无法主动撤销。项目有效期为两小时，用户状态或角色变化后的旧 Token 最长仍可使用到过期。这是已知限制；生产可选短 Token + refresh、版本号或撤销列表。

## 14. Redis 故障为什么选择 fail-open？

Redis 只承载统计缓存和登录/上传限流，不是真源。故障时统计回源 MySQL、限流放行，保住核心业务可用性；代价是频控暂时失效。健康检查仍返回 503，让监控能看到依赖异常。这是明确的可用性与滥用防护取舍。

## 15. 缓存一致性怎么做？

统计使用一个固定 JSON key 和 60 秒 TTL。相关业务事务成功后执行 post-commit 失效；失败事务不清缓存。Redis 异常或 JSON 损坏当作 miss 并回源 MySQL，不让缓存污染业务事实。

## 16. 如何避免指标高基数？

只使用有限的 `outcome`、`flow`、`reason` 标签，禁止任务 ID、用户 ID、文件名、消息 ID和异常文本。否则每个业务对象都会创建新时间序列，导致 Prometheus 内存、存储和查询成本失控。

## 17. 为什么健康检查和业务可用性可能不同？

健康端点检查依赖，因此 Redis 停止时返回 503；但统计回源和限流 fail-open 让部分业务仍返回 200。这不是矛盾：health 表示依赖完整性，业务降级表示服务策略。排障必须同时看两者。

## 18. Docker 镜像如何控制风险？

多阶段构建只把可运行 JAR 放进 Java 17 JRE 镜像，以 UID/GID 10001 非 root 运行，不携带 Maven、源码、`.env` 或构建目录。CI 检查用户、Java 版本和内容；部署只使用完整 SHA 镜像，不使用 `latest`。

## 19. 为什么 Linux 依赖不发布端口？

MySQL、RabbitMQ、Redis 只需被 Compose 网络内的应用访问，发布宿主机端口会扩大攻击面。应用、Prometheus、Grafana 也只绑定回环，通过 SSH 隧道访问。Day 6 还修复了开发 MySQL 原先绑定所有网卡的 Low 问题。

## 20. 数据库迁移如何回滚？

已应用 Flyway 文件不可修改，只新增版本。应用镜像回滚不等于数据库回滚，因此迁移必须评估向后兼容；V11 只是新增索引，对旧应用兼容。真正破坏性迁移需要 expand/contract 和独立数据恢复方案。

## 21. 性能优化为什么只加一个索引？

先用认证 JMeter、Prometheus、50,002 行真实数据的 `EXPLAIN ANALYZE` 对齐瓶颈，再新增与默认 `ORDER BY created_at DESC,id DESC LIMIT 20` 一致的 V11 索引。SQL 从全表扫描/排序变为取 20 行的索引扫描。没有证据就不继续加索引，避免写放大和维护成本。

## 22. 为什么不能宣称性能提升百分比？

优化后 ECS 外部 JMeter 因 JWT 传递损坏全部返回 401，这不是同一业务负载，不能与优化前对比。容器内单请求 200 和 EXPLAIN 证明功能与访问路径，但不足以给出吞吐/P95 改善比例。诚实边界比漂亮数字更重要。

## 23. 如何区分产品缺陷和验收环境问题？

先复现、缩小变量并检查独立证据。Day 6 RabbitMQ 测试最初被常驻消费者抢消息；暂停竞争消费者后契约通过。第一次全回归因隔离库残留 Bootstrap 用户污染；重建仅 Day 6 卷后无需改业务代码即全绿。根因定位后只修验收隔离/清理。

## 24. 项目中最重要的测试策略是什么？

单元测试覆盖纯规则和状态转换，集成测试覆盖真实 MySQL/RabbitMQ/Redis 与 Spring Security，HTTP 验收覆盖 JWT/RBAC 和业务闭环，Compose 验收覆盖六服务/监控/重启，CI 再独立运行完整包和镜像检查。不能用某一层通过代替其他层。

## 25. 如果继续迭代，优先做什么？

先补生产基础：TLS/反向代理、集中秘密管理、备份与恢复演练、SBOM/依赖扫描门禁、告警通知。业务规模真正增长后，再根据指标评估归档分区、消费扩容和服务拆分，而不是预先微服务化。

## 2. Redis 中断、降级与恢复

### 现象

基线时 `/actuator/health` 和 `/api/statistics/overview` 都返回 200。停止隔离 Redis 后，健康检查返回 503，但重新登录和统计接口仍返回 200。恢复 Redis 后健康检查和统计接口都恢复为 200。

### 假设

Redis 是缓存和限流依赖，不是业务事实真源。Redis 不可用时，健康检查应暴露依赖异常；统计应回源 MySQL；登录限流应按既有可用性决策 fail-open，不能让核心登录和读取一起失效。

### 证据

| 检查点 | 结果 |
| --- | ---: |
| 中断前健康检查 | 200 |
| 中断前统计接口 | 200 |
| Redis 停止后健康检查 | 503 |
| Redis 停止后登录 | 200 |
| Redis 停止后统计接口 | 200 |
| Redis 恢复后健康检查 | 200 |
| Redis 恢复后统计接口 | 200 |

脚本只执行 `stop redis` 与 `start redis`，随后用带认证的 `redis-cli ping` 和 HTTP 健康轮询确认恢复。

### 根因与恢复

503 的直接原因是 Redis 健康组件无法连接；统计服务捕获缓存异常并查询 MySQL，限流守卫捕获 Redis 异常并执行 fail-open。重新启动同一个 Redis 容器后连接恢复，应用无需重启。

### 预防

- 保留健康检查告警，不能把 fail-open 误写成依赖健康。
- 核心幂等、权限和业务事实继续由 MySQL/RabbitMQ 约束保护。
- 演练脚本固定项目名并禁止卷删除，避免把可用性演练变成数据恢复演练。

## 3. RabbitMQ 两级重试与 DLQ

### 现象

第一次执行聚焦测试时，两个用例都失败：瞬时失败路径约 1 秒即完成，持续失败路径意外得到 `COMPLETED`。这与既有 5 秒和 30 秒两级延迟契约不符。

### 假设

故障注入只存在于测试进程的 Spy 消费者中，而隔离 Compose 应用也在监听同一队列；常驻消费者可能先抢到消息，绕过注入。

### 证据

- 首次结果：2 个测试、2 个失败；瞬时路径耗时 `1068 ms`，持续路径期望 `FAILED` 但实际为 `COMPLETED`。
- 隔离应用和测试进程同时连接 `finguard-day6` RabbitMQ，且监听相同对账队列。
- 演练脚本新增“停止隔离 app → 运行测试 → 启动 app 并等待健康”的受控边界后，两个测试 2/2 通过，0 失败、0 错误、0 跳过，总 Maven 用时约 64 秒。
- 持续故障最终消息头为 `x-finguard-retry-attempt=2`、失败码 `RETRY_EXHAUSTED`，任务为 `FAILED`，没有对账结果重复写入；测试夹具清空相关队列与数据库行。

### 根因与恢复

首轮失败是演练消费者竞争，不是重试实现缺陷。通过暂停同一隔离项目的常驻应用消费者，使测试 Spy 成为唯一消费者；`finally` 中重新启动应用并等待 `/actuator/health=200`，恢复完整栈。

### 预防

- 消费者故障注入必须保证目标队列只有受控消费者。
- 演练脚本必须在 `finally` 中恢复应用并轮询健康。
- 重试验收同时断言时间、终态、DLQ 头、结果数量和清理，不能只看 Maven 退出码。

## 4. 错误 MySQL 配置与恢复

### 现象

使用 `MYSQL_PORT=1` 启动一次性应用容器后，容器按预期以 `exited|1` 退出；日志出现数据库连接失败根因。删除该容器后，原隔离应用健康检查仍为 200。

### 假设

错误依赖地址应在应用启动期由数据源/Flyway 快速暴露，并且一次性诊断不应改写环境文件、重建依赖或破坏健康实例。

### 证据

| 检查点 | 结果 |
| --- | --- |
| 故障注入 | 一次性 `app`，`--no-deps`，`MYSQL_PORT=1` |
| 故障容器状态 | `exited|1` |
| Compose 运行退出码 | 1 |
| 日志根因 | 数据库连接不可用 |
| 一次性容器 | 已删除 |
| 原应用恢复/保持健康 | HTTP 200 |

演练第一次还发现清理脚本会把“不存在旧容器”的 Docker 错误当成致命错误。已用测试锁定幂等要求，并改为先 `docker container inspect`，仅在存在时删除。

### 根因与恢复

故障容器使用无效端口，数据源无法建立 MySQL 连接，Spring 上下文启动失败。原应用和依赖没有被替换，因此移除一次性容器即完成恢复。

### 预防

- 部署前执行 Compose 配置解析和依赖健康检查。
- 错误配置诊断使用一次性、无依赖重建的容器，禁止直接修改保留环境文件。
- 清理逻辑必须幂等，并且只接受固定的 Day 6 容器名。

## 5. 演练结论

三项故障均在隔离环境中得到“现象 → 假设 → 证据 → 根因 → 恢复 → 预防”的完整闭环。Redis 中断符合预期降级，RabbitMQ 两级重试/DLQ 在排除竞争消费者后符合契约，错误 MySQL 配置能够快速失败且不影响健康实例。演练过程中发现的两个问题都位于演练隔离/清理脚本，并已通过失败测试后做最小修正。

演练结束后，`finguard-day6` 的容器、网络、命名卷、消息/测试行、临时环境与密码文件均已清理；扫描结果和缓存也已删除。普通开发 MySQL、RabbitMQ、Redis 未停止、未重建、未删除数据卷。

# FinGuard Core 产品需求文档

- 文档状态：已实现并完成 Week 6 最终验收
- 最后更新：2026-08-13
- 事实来源：[项目交接说明](../PROJECT_BRIEF.md)、[任务与验收记录](../TASKS.md)、[Week 6 最终复盘](review/week6-review.md)

## 1. 产品定位

FinGuard Core 是一个面向 Java 后端工程学习和实习展示的交易导入、自动对账与异常审核平台。它用一条可验证的业务闭环训练数据正确性、异步可靠性、权限分离、审计、监控、部署和故障恢复，而不是堆叠与问题无关的技术。

本项目是个人工程实践，不是生产金融系统，不承载真实客户、资金或合规责任。

## 2. 目标用户与问题

| 用户 | 核心任务 | 需要解决的问题 |
| --- | --- | --- |
| `ADMIN` | 管理账户/交易、上传文件、发起对账、查看审计统计 | 批量数据容易重复、格式错误，数据库与消息之间需要可靠衔接 |
| `REVIEWER` | 查看业务数据并对风险任务做决定 | 异常交易需要独立角色、并发保护和完整审计 |
| 项目维护者 | 构建、部署、监控、排错和回滚应用 | 需要可重复验收、最小暴露面和证据明确的恢复流程 |

## 3. 产品目标

1. 从 CSV 文件可靠地产生可追踪的交易导入任务。
2. 对内部交易执行可重复、可审计的自动对账。
3. 通过确定性风险规则生成审核任务，并由独立角色决策。
4. 用 MySQL、RabbitMQ、Redis 和业务指标交叉证明业务终态。
5. 让项目能够通过自动化测试、六服务运行验收、部署脚本和文档独立重建与讲解。

## 4. 核心用户旅程

```text
登录并获取 JWT
  → ADMIN 创建账户/交易或上传 CSV
  → 文件 SHA-256 去重并创建异步导入任务
  → RabbitMQ 消费、逐行校验和事务入库
  → ADMIN 发起自动对账并等待终态
  → 风险规则命中并生成审核任务
  → REVIEWER 以版本号完成决策
  → 审计、统计、MySQL、MQ、Redis、Prometheus/Grafana 相互核对
```

## 5. 功能需求

### FR-01：认证与权限分离

系统必须提供匿名登录入口并签发 JWT。账户、交易和任务读取允许 `ADMIN`、`REVIEWER`；业务写入只允许 `ADMIN`；审核决定只允许 `REVIEWER`。缺少/无效身份返回 401，身份有效但角色不足返回 403，拒绝的写请求不得产生数据库副作用。

### FR-02：账户与交易管理

系统必须支持账户和人工交易的创建、查询、修改、软删除及分页筛选。账户号全局唯一；金额必须使用确定精度；新交易必须属于有效账户；导入交易还必须受来源外部流水号唯一约束。

### FR-03：CSV 文件接收与去重

系统必须计算上传内容的 SHA-256，在同一账户范围内识别重复文件，并返回已存在任务而不是重复导入。文件必须按既定表头、编码、行数、金额、日期和字段规则校验。

### FR-04：异步导入

系统必须通过事务 Outbox 发布导入消息，由 RabbitMQ 消费者处理文件；任务从待处理进入处理中和明确终态。重复投递、消费者重启或数据库唯一键冲突不得产生重复交易；失败任务必须保留可诊断的错误摘要。

### FR-05：自动对账

系统必须按账户和业务日期创建对账任务，对金额、方向、日期和外部流水事实进行匹配，产出匹配、未匹配、重复或可疑结果。同一业务请求必须幂等，重复提交不得创建第二个有效任务。

### FR-06：风险与审核

系统必须在真实业务完成后执行确定性风险规则，并为命中事实创建审核任务。`REVIEWER` 必须携带当前版本决策；并发旧版本更新必须失败，终态任务不得被重复决定。

### FR-07：审计与统计

登录、业务写入、导入、对账和审核等关键动作必须形成不包含原始秘密的审计记录。统计以 MySQL 为事实源，Redis 只缓存固定统计结果并设置有限 TTL；数据变更提交后必须使相关缓存失效。

### FR-08：运维与证据

系统必须提供健康、OpenAPI、Prometheus 指标和 Grafana 仪表盘；提供 Java 17 容器、六服务 Compose、CI、完整 Git SHA 镜像发布、Linux 部署/回滚脚本和隔离验收入口。每个完成结论必须能指向自动化或真实运行证据。

详细接口、权限和错误码见 [API 文档](API.md)，数据实体、索引和约束见 [数据库文档](DATABASE.md)。

## 6. 非功能需求

### NFR-01：正确性与幂等

MySQL 是任务、业务和审计事实源；文件哈希、业务唯一键、任务行锁、终态判断和乐观锁共同抵抗重试与并发。RabbitMQ 采用至少一次语义，系统不声称 Exactly Once。

### NFR-02：安全

口令使用 BCrypt，JWT 密钥和服务凭据只通过运行环境提供；应用以非 root 用户运行；开发依赖端口绑定回环，Linux 依赖端口不发布；Actuator 仅暴露 health 和 prometheus。当前安全边界及限制见 [安全测试报告](SECURITY_TEST_REPORT.md)。

### NFR-03：可靠性与恢复

Outbox 降低数据库与消息双写窗口；消费者使用手动 ACK、有限重试和 DLQ。Redis 不可用时统计回源 MySQL、限流 fail-open；MySQL 不可用时应用快速失败并暴露不健康。恢复必须重新验证业务事实和监控，而不只看进程存在。

### NFR-04：性能

优化必须同时具备认证请求、Prometheus 和真实 MySQL 执行计划证据。当前只确认默认审计分页的复合索引访问路径，不外推生产吞吐、并发容量或生产 SLA，详见 [性能报告](PERFORMANCE_REPORT.md)。

### NFR-05：可观测性

Prometheus 必须抓取应用 target，Grafana 必须自动装载数据源和仪表盘；导入完成、对账耗时和消息消费失败指标只能使用低基数标签，不得携带用户、文件、任务、交易、JWT 或异常原文。详见 [监控文档](MONITORING.md)。

### NFR-06：部署与回滚

CI 必须在测试与镜像检查通过后发布完整 40 位 Git SHA 标签。Linux 部署使用私有依赖拓扑和命名卷；回滚只切换应用镜像并保留卷，不回滚 Flyway、业务数据或外部副作用。详见 [部署文档](DEPLOYMENT.md)。

### NFR-07：可测试与可交接

项目必须同时保留单元/集成测试、隔离六服务验收、文档链接与秘密检查、清理检查和托管 CI 证据。当前新鲜验收为 Java 17 测试 379/379、Flyway V11、OpenAPI 18 条路径和六服务业务闭环；详情以 [Week 6 最终复盘](review/week6-review.md) 为准。

## 7. 范围外

- 前端、移动端、MinIO 和真实银行/支付渠道集成；
- 微服务拆分、Kubernetes、Service Mesh、OpenTelemetry、ELK；
- 当前不包含多可用区、高可用数据库、自动备份恢复和灾备承诺；
- JWT 主动撤销/刷新、企业级秘密管理和完整合规认证；
- 当前不提供生产容量、生产 SLA、零漏洞或 Exactly Once 保证。

## 8. 已知限制

1. 运行模型是单机 Docker Compose，没有 TLS、负载均衡或多可用区。
2. JWT 没有刷新与主动撤销，旧 Token 在有效期内仍可使用。
3. Redis 限流 fail-open 会在故障期间暂时削弱频控。
4. ZAP 证据是未认证被动基线，不等于完整渗透测试。
5. 有效性能证据只覆盖审计默认分页；优化后一次全 401 外部复测已作废。
6. 应用镜像回滚不等于数据库回滚或灾难恢复。

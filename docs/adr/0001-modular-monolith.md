# ADR-0001：使用模块化单体

日期：2026-08-13

## 状态

Accepted

## 背景

FinGuard Core 需要在一个六周 Java 后端项目中覆盖认证、账户/交易、CSV 导入、对账、风险审核、审计、缓存、消息和可观测性。核心流程共享同一业务事实和多处事务边界，但当前没有独立团队、独立发布节奏或容量证据支持分布式拆分。

## 决策

采用单个 Spring Boot 应用和单个可部署镜像，在源码中按 `auth`、`account`、`transaction`、`importjob`、`reconciliation`、`risk`、`review`、`audit`、`messaging`、`redis` 等业务职责分包。跨模块通信优先使用明确服务接口；只有异步可靠性需要时才经过 Outbox/RabbitMQ。

## 理由

- 保留清晰的数据库事务边界，便于证明导入、对账、风险和审计一致性。
- 一套构建、部署和监控链即可覆盖完整业务闭环，适合个人项目的时间与运维能力。
- 模块边界仍能训练职责分离，未来只有在团队、容量和独立发布证据出现后才考虑拆分。

## 后果

正面后果是本地开发、自动化测试、部署和排错更直接，跨模块调用无需分布式事务。负面后果是应用统一扩缩容、故障域共享，模块边界需要依赖代码纪律而不是进程隔离。

本决策不声称高可用，也不把单体等同于无结构代码。

## 替代方案

- **按业务拆微服务**：增加服务发现、网络失败、数据所有权和分布式一致性成本；当前无证据证明收益大于成本。
- **Kubernetes 部署**：不能自动解决应用边界、数据库可用性或个人项目容量问题，因此不纳入当前范围。
- **单包分层应用**：实现更快，但业务职责会混在 controller/service/mapper 横向层中，不利于学习和维护。
